# 07 重定位改造方案

> 目标：把仓库里的 `btc_place_recognition`（同一条序列内的回环检测）改造成**先验地图中的全局重定位**——机器人被放到已建图的环境中，用当前若干帧扫描估计一个大致初始位姿（map→base_link 的 6DoF 或 4DoF）。
>
> 本文只给方案与改动清单，不含实现。文中所有结论都标了 `文件:行`，可逐条复核；标注"待实测"的地方是需要在 M0 阶段用数据确定的。

---

## 0. 结论

**需要改，但不是重写。**

现有的 `GenerateBtcDescs → candidate_selector → candidate_verify → plane_geometric_verify` 这条链路本身是 6DoF、且与"查询点云在哪个坐标系"无关；真正卡住重定位的是三件事：

1. **二值描述子依赖地图系朝向**：示例先用真值位姿把点云变到世界系再提描述子（`src/example/place_recognition.cpp:176`），而 `extract_binary` 的投影基由**全局 X 轴**构造（`src/src/btc.cpp:1103`）。查询帧在传感器系、偏航未知时，二值相似度门控会失效。
2. **库与查询没有分离**：`data_base_` 只在内存里、`BTC::frame_number_` 是 `unsigned short`（`src/include/btc.h:84`）、投票数组是栈上定长 `match_array[20000]`（`src/src/btc.cpp:1584`），承载不了"离线建库 + 在线查询 + 上万关键帧"。
3. **只输出一个最优候选，没有多帧融合、没有失败判定、没有初始位姿接口**：`SearchLoop` 只返回 best（`src/src/btc.cpp:584`），节点是一次性批处理器（`src/example/place_recognition.cpp:119`、`:370`），不订阅话题、不发 `/initialpose`。

**工作量估计**：核心库改动约 300 行，新增建库/序列化/查询模块与两个节点约 800–1200 行，配置与 launch 约 100 行；单人 3–4 周（含评测）。

## 1. 现状与重定位需求的差距

### 1.1 描述子只对平移不变，对旋转敏感（最关键的一条）

代码事实：

| 环节 | 位置 | 性质 |
| --- | --- | --- |
| 三角形编码（三边长量化） | `src/src/btc.cpp:1433` `generate_btc` | **旋转 + 平移不变** |
| 平面法向翻到 +z | `src/src/btc.cpp:1049` | 依赖"z 轴朝上"的约定 |
| 投影基 `x_axis` 取全局 X | `src/src/btc.cpp:1103` | **依赖全局朝向** |
| `y_axis = normal × x_axis` | `src/src/btc.cpp:1113` | 同上 |
| 占据位图相似度 | `src/src/btc.cpp:107` `binary_similarity` | 逐位比较，无对齐 |

推论：

- **BTC 的三角形部分**只用了三边长与顶点位置，任意刚体变换下不变 → 检索哈希（`BTC_LOC`，`src/include/btc.h:141`）与 `triangle_solver`（`src/src/btc.cpp:1831`）解出的 (R, t) 都是 6DoF、与初始朝向无关。
- **二值部分**的 2D 网格基由"平面法向 + 全局 X 轴"决定；查询帧绕 z 转 θ，点云图案相对网格转了 θ，格点编号整体错位。`occupy_array_` 只有 50 位（`cut_num = (proj_dis_max - proj_dis_min)/proj_image_high_inc = (4-(-1))/0.1`，`src/src/btc.cpp:1239`），`binary_similarity` 是 Dice 系数逐位对齐比较，转 10°~20° 就足以让相似度从 0.9 掉到 0.5 以下（待 M0 量化）。
- 示例之所以能跨回访匹配，是因为**两次回访的点云都先被真值位姿变到了同一个世界系**（`src/example/place_recognition.cpp:176`），二值模板天然同源。

所以：**重定位的第一决策是"查询帧的偏航怎么处理"**（见 §3.1），其余都是工程量。

### 1.2 库与查询没有分离

- `data_base_`、`key_cloud_vec_`、`plane_cloud_vec_`、`history_binary_list_` 都是常驻内存的成员（`src/include/btc.h:299-309`），没有序列化/加载接口。
- 帧号即数组下标：`BTC::frame_number_` 是 `unsigned short`（`src/include/btc.h:84`），投票用 `match_array[20000]`（`src/src/btc.cpp:1584`）→ 关键帧超过 20000 直接越界写，超过 65535 帧号回绕、时间过滤失效。
- `candidate_verify` 用 `plane_cloud_vec_.back()` 当前帧（`src/src/btc.cpp:1823`），把"当前帧"隐式绑成"最后一个 push 的帧"（docs/05 §3.6），不能多帧并行、也不能先建库后查询。

### 1.3 时间过滤、单候选与阈值

- 节点侧 `if (submap_id > config_setting.skip_near_num_)`（`src/example/place_recognition.cpp:195`），检索侧 `(当前帧号 - 历史帧号) > skip_near_num_`（`src/src/btc.cpp:1632-1634`）→ 默认只和"至少早 100 帧"的帧比。重定位要允许匹配**任意**关键帧，包括第 0 帧。
- 好消息：`config_indoor.yaml` 的注释已经写明 `skip_near_num` 设成 `-1000000` 就是给 inter-machine（跨机/跨 session）用的，所以"关掉时间过滤"这一项**纯配置即可**，不用改代码。
- 但还有两处必须改：`SearchLoop` 只返回一个 best（`src/src/btc.cpp:584`），且调用方用 `> 0` 判定（`src/example/place_recognition.cpp:202`）→ **匹配到关键帧 0 永远报告不出来**；重定位还需要 top-K 与失败判定。

### 1.4 节点形态

`while (ros::ok() && !finish)` 一次性跑完整个目录后 `finish = true` 退出（`src/example/place_recognition.cpp:119`、`:370`），不订阅点云、不发位姿。重定位需要常驻节点、滑窗触发、服务/话题输出。

### 1.5 对照表

| 维度 | 现状 | 重定位需要 |
| --- | --- | --- |
| 描述子坐标系 | 地图系（靠真值变换） | 传感器系查询，自动对齐朝向 |
| 数据库 | 进程内、随序列增长 | 离线建库、落盘、加载 |
| 帧号/容量 | u16 + 定长 20000 数组 | u32 + 动态容器，支持 10⁴–10⁵ 关键帧 |
| 时间过滤 | 跳过最近 100 帧 | 关闭（配置可关）或按"是否同 session" |
| 输出 | 单候选 + 3 点 SVD | top-K + 多帧融合 + 置信度 + `/initialpose` |
| 运行形态 | 批处理评估器 | 常驻节点 + 服务/话题 |
| 失败处理 | 无 | 明确"未定位"，不产生错误 TF |

## 2. 目标、输入输出与验收

### 2.1 输入

- **先验地图**（二选一）：
  1. 关键帧目录 + 位姿文件（推荐）：`keyframes/000000.pcd …` + `poses.txt`（`id x y z qx qy qz qw`，与 `src/example/place_recognition.cpp:100` 用的 `load_evo_pose_with_time` 同格式）。点云若是激光系就按位姿变换到地图系再建库。
  2. 单张已拼接的大地图 PCD：按**轴对齐**立方块（20–30 m）切块，块内点云保持地图系坐标、块位姿取单位阵。**只能平移切块、不能旋转切块**——原因见 §1.1。
- **查询**：机器人当前 N 帧（建议 5–10 帧，覆盖 1–3 s）、每帧在传感器系，附带一个里程计相对位姿 `T_odom←sensor_k`（没有的话退化成一帧一查）。
- **坐标约定**：地图必须是 z 轴朝上、单位为米——`binary_extractor` 用 `if (proj_normal.z() < 0)` 把法向翻到 +z（`src/src/btc.cpp:1049`），这条约定隐含在二值模板里。LIO/SLAM 输出通常已重力对齐，可直接落库；否则建库前先做一次对齐。

### 2.2 输出

- `geometry_msgs/PoseWithCovarianceStamped` 发布到 `/initialpose`（`frame_id = map`），即 RViz "2D Pose Estimate" 的语义，便于现成导航栈消费。
- `nav_msgs/Odometry` 发布到 `/relocalization/pose`（含协方差）。
- 服务 `/relocalize`（`std_srvs/Trigger`）：手动触发一次，`success` 表示是否定位成功。
- 可选：一次性发布 `map→odom` 修正 TF（把当前里程计对齐到地图），发布后进入"已定位"状态，不做持续定位。
- 状态话题 `/relocalization/status`（`std_msgs/String` 或 MarkerArray）：`SEARCHING / FOUND / FAILED` + 匹配关键帧 id + 分数。

### 2.3 验收指标

| 指标 | 目标 |
| --- | --- |
| 成功率（平移 < 1.0 m 且偏航 < 5°） | ≥ 90%（室内结构化场景，M0 数据确定基线） |
| 中位误差 / P95 误差 | < 0.5 m / < 1.5 m |
| 单次重定位耗时（10 帧） | < 1 s；最差 < 3 s |
| 误报率（判成功但误差 > 5 m） | < 1% |
| 失败可检测性 | 场景外/无重叠时能返回 FAILED，不产生错误 `/initialpose` |

### 2.4 评测数据

- **伪重定位**（本仓现有数据即可做）：`building03` 1707 帧，取 0–700 帧建库（按 ≥2 m 抽稀），从 800–1700 帧随机抽 100 帧做查询，屏蔽真值位姿，与 `pose.txt` 比对。
- **朝向鲁棒性**：查询帧绕 z 随机旋转 0–360° 后再送入，模拟"不知道朝向"。
- **跨 session**：需要另采一次同场景数据；没有之前先把 `skip_near_num` 设成 `-1000000`（`config_indoor.yaml` 注释里推荐的跨机取值）做"同 session 不同时段"近似。
- 真值交叉核验：`calc_overlap`（`src/src/utils.cpp:218`）——现有节点用它做真阳判定（`src/example/place_recognition.cpp:260`），可直接复用为"位姿是否落在地图重叠区"的独立检查。

## 3. 关键技术决策

### 3.1 决策一：查询帧的朝向怎么处理（三选一，M0 用数据定）

| 方案 | 做法 | 成本 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 偏航假设搜索 | IMU/里程计保证 roll/pitch，绕 z 枚举 36×10° 偏航，逐个提描述子检索 | 单帧 ~36×检索时间，粗搜 12 档可降到 1/3 | 慢；偏航精度受格点量化限制 | 保底方案 |
| **B. 关掉二值门控做检索** | 只用三角形边长检索投票，`triangle_solver` 直接解 6DoF，`plane_geometric_verify` 打分 | 与现有流程同量级 | 候选变多、误报上升，需重调 `candidate_num`/`icp_threshold` | **推荐** |
| C. 改造描述子为旋转不变 | 用平面点云 PCA 主轴代替全局 X 构基 + 符号规范化 | 大（DB 与查询都要重算） | 近各向同性平面主轴不稳定，退化场景多 | 不建议先做 |

推荐 **B + 复核**（记作 B+）：

1. 检索阶段把二值相似度门控关掉（等价于 `similarity_threshold = 0`，或新增 `use_binary_gate_in_retrieval: 0`）；
2. 候选帧由"三角形边长投票"产生，`candidate_verify` 用 3 点 SVD 解 (R, t)（`src/src/btc.cpp:1831`），`plane_geometric_verify` 打分（`src/src/btc.cpp:1855`）；
3. 成功后再用解出的 R 把查询帧变到地图系、重算二值描述子，与命中关键帧做一次相似度**复核**——把二值从"检索门控"降级为"验证项"，几乎零额外成本。

依据：三角形检索、3 点 SVD、平面校验三步都与查询点云的坐标系无关（§1.1 表格），唯一依赖朝向的是门控。

B 的主要风险是**候选爆炸**：去掉门控后同一边长三元组会命中大量关键帧，`match_array` 里票数分布变平，`candidate_num=50` 可能不够、耗时上升。M0 必须量化。

### 3.2 决策二：库/查询分离与落盘

- 新增 `btc_build_database`（离线，读关键帧目录 + 位姿 → 写 DB 文件）与 `btc_relocalization`（在线，加载 DB → 查询）。
- DB 文件里必须存**配置指纹**：`proj_image_high_inc`、`proj_dis_min/max`（决定 `cut_num` 即位图长度）、`proj_image_resolution`（格点尺寸）、`proj_plane_num`（模板个数）、`triangle_resolution` 等任一变化都会让描述子含义变化；而 `binary_similarity` 是按 `b1.occupy_array_.size()` 遍历、直接索引 `b2`（`src/src/btc.cpp:107-116`），**长度不一致会越界读**。加载时校验指纹，不一致直接拒绝。
- 地图来源用"关键帧 + 位姿"优先；单张大地图只能轴对齐切块（§2.1）。

### 3.3 决策三：索引与容量

| 改动 | 现状 | 改为 | 理由 |
| --- | --- | --- | --- |
| 帧号类型 | `unsigned short`（`btc.h:84`） | `uint32_t` | 关键帧数上万 |
| 投票容器 | `double match_array[20000]`（`btc.cpp:1584`） | `std::vector<int> votes(n_keyframes, 0)` | 定长栈数组，超 20000 越界 |
| 当前帧耦合 | `plane_cloud_vec_.back()`（`btc.cpp:1823`） | 显式传 `source_plane_cloud` 参数 | 解锁"先建库后查询"与并行 |
| 时间过滤 | 两处硬编码比较（`place_recognition.cpp:195`、`btc.cpp:1632`） | 检索侧改为 `skip_near_num_ < 0` 时整段跳过；节点侧条件在负数下恒成立、天然放行 | 配置即可关闭；只需给检索侧加一条分支 |
| 单候选 | `SearchLoop` 只返回 best（`btc.cpp:584`） | 新增 `SearchTopK(k)`，返回 top-K 的 (frame_id, score, (R,t)) | 多帧融合要用 |
| 候选 id 0 | 调用方 `> 0`（`place_recognition.cpp:202`） | `>= 0` / `!= -1` | 关键帧 0 是合法匹配 |

### 3.4 决策四：多帧融合

单帧重定位误报率天然高，必须多帧一致才判成功。**在里程计系里融合**，而不是直接平均各帧位姿：

```
第 k 帧成功 → 得到 T_map←sensor_k（= triangle_solver 的 (R,t)，因为 DB 在地图系）
里程计给出 T_odom←sensor_k
故        T_map←odom_k = T_map←sensor_k · (T_odom←sensor_k)⁻¹
对 k 做鲁棒平均（平移取各分量中位数，旋转取四元数平均），得到 T_map←odom
最终      T_map←base = T_map←odom · T_odom←base
```

一致性判定（任一不满足即丢弃该帧，不是丢弃整体）：

- 命中关键帧相同，或空间距离 ≤ 10 m 且偏航差 ≤ 15°；
- 该帧解出的 `T_map←odom_k` 与当前鲁棒均值差 ≤ `pose_cluster_trans_thr`(1.0 m) / `pose_cluster_yaw_thr`(10°)；
- 且该帧 `plane_geometric_verify` 分数 ≥ `icp_threshold`。

判成功条件：内点帧数 ≥ `min_inlier_frames`（建议 3）且窗口已满（或服务被手动触发）。协方差由内点残差（平移/偏航的 MAD）给出，直接写进 `PoseWithCovarianceStamped`。

### 3.5 决策五：精化

- `triangle_solver` 只用 3 个顶点，位姿噪声在厘米–分米级但可能被单点误差放大；`PlaneGeomrtricIcp`（`src/src/btc.cpp:669`）已实现、从未接线（docs/05 §4.1），正好用作精化：以 3 点 SVD 结果为初值，对命中关键帧的 `plane_cloud_vec_` 做点到面 ICP。
- 更强但更重的替代：对命中关键帧的降采样点云做 NDT/GICP（PCL 自带 `pcl::NormalDistributionsTransform` / `pcl::GeneralizedIterativeClosestPoint`），精度更高，代价是 10–50 ms/次，可按需开启。
- 精化只做一次（对最终融合位姿），不要对每个候选做。

### 3.6 决策六：输出接口

| 接口 | 类型 | 说明 |
| --- | --- | --- |
| `/initialpose` | `geometry_msgs/PoseWithCovarianceStamped` | RViz/导航栈通用入口，`frame_id=map` |
| `/relocalization/pose` | `nav_msgs/Odometry` | 带协方差，便于程序消费 |
| `/relocalize` | `std_srvs/Trigger` | 手动触发；成功时同上发布 |
| `/relocalization/status` | `std_msgs/String` | `SEARCHING/FOUND/FAILED` + id + score |
| `map→odom` TF（可选） | TF | 仅在 FOUND 时发布一次，避免"半定位"污染 TF 树 |

## 5. 新增模块与接口

### 5.1 数据结构

```cpp
// 关键帧元数据（DB 里与描述子一一对应）
struct MapKeyframe {
  uint32_t id;                 // 稠密下标，即 BTC::frame_number_
  Eigen::Vector3d t;           // T_map<-keyframe
  Eigen::Matrix3d R;
};

// 一次重定位的结果
struct RelocalizationResult {
  bool success = false;
  uint32_t matched_keyframe = 0;
  double score = 0.0;          // plane_geometric_verify 分数
  int inlier_frames = 0;       // 一致帧数
  Eigen::Vector3d t_map_base;  // 输出位姿
  Eigen::Matrix3d R_map_base;
  Eigen::Matrix<double, 6, 6> covariance;
};
```

### 5.2 `MapDatabase`（`src/include/map_database.h`）

```cpp
class MapDatabase {
 public:

### 5.4 DB 文件格式（建议）

```
magic "BTCDB01" | uint32 version | uint64 config_hash | uint32 n_keyframes
per keyframe: uint32 id | double pose[7] | uint32 n_btc | uint32 n_planes
per BTC:      float triangle[3] | float center[3] | float angle[3] | uint32 frame_id
              ×3 binary: { uint32 nbits | packed bits | uint8 summary | float loc[3] }

体积估算：二值描述子 50 bit（`src/src/btc.cpp:1239`），单个约 40 B，一个 BTC 约 200 B；单帧 200–500 个 BTC → 40–100 KB；1707 关键帧约 0.1–0.2 GB（含平面云），可接受；更大规模再按 keyframe 抽稀。

## 8. 评测协议

1. **切库**：0–700 帧落库（按 ≥2 m 抽稀成关键帧），DB 落盘。
2. **查询**：800–1700 帧随机 100 帧；每帧绕 z 随机旋转（0–360°）后作为传感器系点云送入，模拟未知朝向；同时喂该帧的"里程计相对位姿"（用真值相邻帧相对位姿代替）。
3. **判定**：与 `pose.txt` 比对，平移误差 < 1 m 且偏航误差 < 5° 记为成功；判成功但误差 > 5 m 记为误报。
4. **输出**：每帧一行 CSV（`frame, success, t_err, yaw_err, score, matched_id, latency_ms`）；汇总成功率、中位/P95 误差、误报率、耗时分布。
5. **交叉核验**：对判成功的帧跑一次 `calc_overlap(query_cloud, matched_keyframe_cloud, 0.5)`（`src/src/utils.cpp:218`），确认位姿确实落在重叠区，而不是"分数高但位置错"。

## 9. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 二值门控的偏航敏感被低估/高估 | 方案 B 的召回不如预期 | M0 先量化；不行就退方案 A（36 档偏航），或只对"前 3 帧"做偏航搜索、其余帧用解出的位姿 |
| 候选爆炸 | 单帧检索从 9 ms 涨到几十 ms，误报上升 | `candidate_num` 与 `icp_threshold` 联调；先按边长粗排 top-50 再做 6DoF 校验 |
| 对称/长廊场景误报 | 相似走廊里多个关键帧都"看起来对" | 多帧一致性（§3.4）+ `calc_overlap` 复核 + 位姿协方差门限 |
| DB 过大/内存 | 城区级地图上 GB 级内存 | 关键帧抽稀、二值描述子位压缩、`plane_cloud_vec_` 按需懒加载 |
| 配置指纹不一致 | `binary_similarity` 越界读（长度不同） | DB 里存 config hash，加载即校验 |
| 与上游同步冲突 | `src/src/btc.cpp` 已有本地 Ceres 补丁（`src/src/btc.cpp:4-9`），改检索路径易冲突 | 先提交本地补丁，再开分支改；核心改动尽量收敛在新增文件里 |
| WSL 计时抖动 | 耗时指标不稳 | 评测与基线同机同负载；以相对值为主 |

## 附录 B：为什么三角形不变、二值不变性更弱

设查询点云整体做刚体变换 `p' = R p + t`。

- 三边长 `|p1-p2|`、`|p1-p3|`、`|p2-p3|` 不变 → 量化后的 `BTC::triangle_` 不变 → 哈希键 `BTC_LOC` 不变；顶点相对重心的坐标随 R 旋转，`triangle_solver` 用 SVD 解出的 (R, t) 是同一个 6DoF 量。
- 二值描述子的 2D 基是 `x_axis = normalize(global_X 在平面内的投影)`、`y_axis = n × x_axis`。当 `p' = R p` 且 R 是绕 z 的偏航时，`n' = R n`、`x_axis' ≠ R x_axis`（因为 global_X 没转），于是平面内的点相对网格旋转了 θ，`occupy_array_` 的位编号整体错位；而 `binary_similarity` 是逐位 Dice 系数，不做任何对齐。
- 结论：**检索的"三角形"一路对坐标系免疫，二值一路必须先把查询帧转到与地图一致的朝向上**（或关掉门控，§3.1）。

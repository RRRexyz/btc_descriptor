# 06 输入数据格式规范

本文是 `btc_desc` 的**输入数据契约**：只要你能按这里的规则产出数据，`btc_place_recognition` 就能直接读；反之读不进去时，本文第 10 节的故障表能直接定位原因。

适用对象：想把**自己的数据集 / 仿真数据 / 其他项目的输出**喂给 `btc_desc` 的人。文中所有结论都对照过源码，示例数据在 ROS Noetic + 本仓库当前代码上实跑验证（命令与真实输出见第 8、9 节）。

---

## 0. 生成方需要交付什么

只有三样东西，全部是**磁盘文件**，不需要 ROS、不需要消息格式：

| # | 数据 | 参数名 | 形态 | 读它的代码 | 格式错了会怎样 |
| --- | --- | --- | --- | --- | --- |
| 1 | 点云序列 | `pcds_dir` | 一个目录，内含 `000000.bin` … `%06d.bin`（或 `.pcd`） | `read_lidar_data`（`src/example/place_recognition.cpp:13`） | **静默退出**，只打印 `Read End...` |
| 2 | 位姿文件 | `pose_file` | 一个文本文件，每行 8 列 `id x y z qx qy qz qw` | `load_evo_pose_with_time`（`src/src/utils.cpp:138`） | 行被静默丢弃 / 列错位 → 位姿全错 |
| 3 | 算法参数 | `setting_path` | 一个 OpenCV FileStorage 风格 YAML | `load_config_setting`（`src/src/btc.cpp:12`） | 打不开直接 `exit(-1)`；键名写错则**该参数变 0**，不报错 |

三者的关系：**点云是传感器系下的原始单帧扫描，位姿把这一帧搬到世界系**（`p_world = R · p_sensor + t`），算法只在世界系点云上做平面提取和描述子。所以第 1、2 项必须来自同一套坐标系约定，这是最容易出错、也最难从日志发现的地方。

## 1. 目录约定

```
my_dataset/
├── velodyne/            ← pcds_dir 直接指向这一层
│   ├── 000000.bin
│   ├── 000001.bin
│   ├── ...
│   └── 000239.bin
└── pose.txt             ← pose_file
```

约定与陷阱：

- **`pcds_dir` 必须指向"直接装有帧文件"的目录**。写成数据集根目录（`my_dataset`）会找不到 `my_dataset/000000.bin`，程序只打一行 `Read End...` 就结束。这一条在本项目里实际踩过（`strace` 显示 `openat(".../data/000000.bin") = ENOENT`）。
- 文件名固定 **6 位零填充**（`std::setw(6) << std::setfill('0')`），从 `000000` 起连续递增，格式串是 `%06d`。
- 用**绝对路径**。通过 `roslaunch` 启动时进程工作目录是 `~/.ros`，相对路径会解析到那里。
- 目录里多出来的文件（比如 `000240.bin` 而位姿只有 240 行）不会被读取；少的文件则会中止后续所有帧。
- `roslaunch` 与 `rosrun` 读的都是**全局**参数（代码里是 `ros::NodeHandle nh;` 而不是 `nh("~")`），所以 `rosparam set /pcds_dir ...` 就够，前缀不用加节点名。

最小可跑的数据集是 3 帧（帧数 ≥1 即可跑通流程，只是不会出回环）。

## 2. 点云帧：`%06d.bin`（`read_bin=true`）

### 2.1 字节布局

**裸二进制，无文件头，行主序，每点固定 16 字节**：

| 偏移（每点内） | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0–3 | `float32`，小端 | `x` | 米，传感器系 |
| 4–7 | `float32`，小端 | `y` | 米，传感器系 |
| 8–11 | `float32`，小端 | `z` | 米，传感器系 |
| 12–15 | `float32`，小端 | `intensity` | 任意反射强度/占位值，**算法全程不读** |

文件字节数必须等于 `16 × 点数`。KITTI velodyne 的 `.bin` 就是这个格式（4 × `float32`，x y z intensity），所以本项目直接兼容 KITTI。

真实样例（`docs/examples/gen_synthetic_sequence.py` 生成的第 0 帧，前 3 个点）：

```text
$ xxd -l 48 velodyne/000000.bin
00000000: e89e 5c40 0000 0000 18c1 cdbf 03d8 3343  ..\@..........3C
00000010: 3dd2 5b40 868c f53c 3704 cdbf e9d7 3143  =.[@...<7.....1C
00000020: b621 5c40 17ea 753d 5754 cdbf 17e4 2e43  .!\@.u=WT.....1C
```

对应的 4 个 float32（小端）：

| # | x | y | z | intensity |
| --- | --- | --- | --- | --- |
| 0 | 3.447199 | 0.000000 | −1.607455 | 179.8438 |
| 1 | 3.434707 | 0.029974 | −1.601691 | 177.8434 |
| 2 | 3.439558 | 0.060038 | −1.604136 | 174.8910 |

文件大小 = 22361 点 × 16 B = 357776 B。

读取方式（生成方最常用的两种写法）：

```python
# python: 生成
import numpy as np
pts = np.loadtxt("points.txt")                       # 或任何来源，shape (N, 4)
pts = np.asarray(pts, dtype="<f4")                    # 必须是小端 float32
assert pts.shape[1] == 4
pts.tofile("velodyne/000000.bin")                     # 拍平写出即可，无头
```

```python
# python: 回读校验
a = np.fromfile("velodyne/000000.bin", dtype="<f4").reshape(-1, 4)
print(a.shape)      # (N, 4) -> x, y, z, intensity
```

C++ 侧实际实现（`src/example/place_recognition.cpp:13-31` 与 `:140-152`）：`fread` 一次性读入整个文件，然后 `for (i = 0; i < lidar_data.size(); i += 4)` 每 4 个 float 组一个点。**注意这个 stride 是写死的**，所以 3 通道（x y z）的 `.bin` 不合法：读到最后会越界读，得到垃圾点甚至崩溃；文件大小不是 16 的整数倍时同理。

### 2.2 语义

- **坐标系 = 位姿的传感器系**。第 `k` 帧的点云与 `pose.txt` 第 `k` 行的位姿必须描述**同一个安装点**（KITTI 里是 velodyne 系；你的仿真里就是你定义激光雷达位置与朝向的那个系）。
- z 向上、右手系、单位米——不是硬编码要求（平面检测用 PCA，投影用平面法向，不假设重力方向），但**米是刚性的**：`proj_dis_min/max`、`descriptor_min_len/max_len`、`voxel_size`、`cloud_overlap_thr` 的重叠判定全都按米/立方米解释。
- 与"世界系"的关系：不要在这里预先乘位姿。算法会自己算 `rotation * pv + translation`；如果你已经转到世界系又给了非单位位姿，点云会被**二次变换**。
- 唯一的例外：如果你的数据只有世界系地图、没有逐帧位姿，那就把**位姿写成全零平移 + 单位四元数**，点云直接写世界系坐标，等价于恒等变换。

### 2.3 硬性要求清单

- [ ] 文件名 `%06d.bin`，从 `000000` 开始**连续**，帧数 = `pose.txt` 行数
- [ ] 每帧非空（0 字节文件读出来是空云，与文件缺失同效：`break` 掉整条序列）
- [ ] 每点严格 4 × `float32` LE，文件大小 % 16 == 0
- [ ] 无 `NaN` / `Inf`（`NaN` 会在平面 PCA 里扩散成整帧无效）
- [ ] 单帧点数建议 ≥ 1e4（见第 7 节）

## 3. 点云帧：`%06d.pcd`（`read_bin=false`）

PCD 分支走 PCL 的 `pcl::PCDReader::read()`（`src/example/place_recognition.cpp:169`），目标类型是 `pcl::PointCloud<pcl::PointXYZI>`。

### 3.1 能读的头

实测可用的最小头部（`DATA binary`，本示例生成器 `--format pcd` 的产物）：

```text
# .PCD v0.7 - Point Cloud Data file format
VERSION 0.7
FIELDS x y z intensity
SIZE 4 4 4 4
TYPE F F F F
COUNT 1 1 1 1
WIDTH 22361
HEIGHT 1
VIEWPOINT 0 0 0 1 0 0 0
POINTS 22361
DATA binary
<紧跟 22361 × 16 字节的点数据>
```

- `FIELDS` **必须包含 `x y z`**，顺序任意（PCL 按名字取列）；`intensity` 可省略。
- 实测两种布局都能读入 `PointXYZI`：`FIELDS x y z intensity`（4 列）与 `FIELDS x y z`（3 列，`intensity` 留默认值）。后者的 `SIZE`/`TYPE`/`COUNT` 也相应只写 3 项。
- `TYPE` 用 `F`（float32）。整数类型（`I`/`U`）的 `x y z` 在本算法里没有意义。
- `DATA` 只支持 **`ascii`** 与 **`binary`** 两种。`binary_compressed` 会失败：

  ```text
  $ OPENCV_LOG_LEVEL=WARNING rosrun btc_desc btc_place_recognition
  [ERROR] [...]: Couldn't read file /tmp/btc_synth/pcd_bc/000000.pcd
  ```

  （OpenCV 的 `PCDReader` 不支持 LZF 压缩体，直接返回 −1。）
- `WIDTH × HEIGHT` 与 `POINTS` 要一致，`binary` 模式下实际字节数要够 `POINTS × 每点字节数`，否则解析出缺点/垃圾点。

### 3.2 与 `.bin` 的差异（重要）

| 行为 | `.bin`（`read_bin=true`） | `.pcd`（`read_bin=false`） |
| --- | --- | --- |
| 文件缺失 | 打印 `Read End...`，**`break` 跳出整条序列**，后续帧全不处理 | 打印 `[ERROR] Couldn't read file ...`，**`continue` 跳过这一帧**，序列继续 |
| 格式错误 | 大小不整除 16 时静默读出垃圾/越界 | `read()` 返回 −1，报错跳过 |
| 强度 | 必填（凑第 4 个 float32） | 可选 |

所以**帧文件缺失**在 bin 路径下是"灾难性"的（静默、还打印 `-nan` 的平均耗时），在 pcd 路径下是"吵闹但继续"的。两种都不该出现，用第 8 节的检查脚本卡住。

## 4. 位姿文件 `pose.txt`

### 4.1 行格式

每行 **恰好 8 个 token，用单个空格分隔**，一帧一行，行序 = 帧序（第 0 行对应 `000000.bin`）：

| 列号 | 内容 | 类型 | 说明 |
| --- | --- | --- | --- |
| 1 | `id` / `time` | 任意数值 | 读入 `time_list` 后**从未使用**，可放序号、时间戳、帧号 |
| 2–4 | `x y z` | 米 | 平移分量，**传感器系原点在世界系中的位置** |
| 5–8 | `qx qy qz qw` | 无量纲 | 旋转四元数，**实部 w 在最后一列** |

真实样例（本示例数据前 3 行，传感器在 (4,4,1.6) 沿 +x 走）：

```text
0 4.000000 4.000000 1.600000 0.000000 0.000000 0.000000 1.000000
1 4.400000 4.000000 1.600000 0.000000 0.000000 0.000000 1.000000
2 4.800000 4.000000 1.600000 0.000000 0.000000 0.000000 1.000000
```

仓库自带的 KITTI 文件 `src/poses/kitti00.txt` 同格式（4541 行，对应 KITTI 00 的 4541 帧），可直接对照：

```text
1 0.692931 0.003604 0.009675 0.001254 -0.000816 0.001655 0.999998
2499 275.769000 -64.447900 2.582320 0.010471 0.003050 0.033638 0.999376
```

### 4.2 四元数顺序：文件里 w 在最后

`src/src/utils.cpp:166-167`：

```cpp
Eigen::Vector3d translation(temp_matrix[0], temp_matrix[1], temp_matrix[2]);
Eigen::Quaterniond q(temp_matrix[6], temp_matrix[3], temp_matrix[4],
                     temp_matrix[5]);
single_pose.second = q.toRotationMatrix();
```

`Eigen::Quaterniond` 的构造参数顺序是 **(w, x, y, z)**，而这里是 `(col8, col5, col6, col7)`，等价于文件列序 **`x y z qx qy qz qw`**。这就是常见的 "xyz + xyzw" 写法（`evo` 的 TUM 格式、很多 SLAM 输出的 `x y z qx qy qz qw` 都是这个顺序），直接照抄即可。

**必须是单位四元数**：代码不做归一化，直接把 `q.toRotationMatrix()` 当旋转用。非单位四元数不会报错，但会得到带缩放的矩阵，把所有点拉变形。实测把 `qz,qw` 同乘 2（`||q||=2`）后，同一帧的参考平面中心 z 从 `1.53` 变成 `3.11`——数据看着"能跑"，结果全错。

生成时按 yaw 角写就行：

```python
import numpy as np
def pose_line(idx, x, y, z, yaw):
    qz, qw = np.sin(yaw / 2.0), np.cos(yaw / 2.0)   # 绕 z 轴
    return "%d %.6f %.6f %.6f %.6f %.6f %.6f %.6f" % (idx, x, y, z, 0.0, 0.0, qz, qw)
```

### 4.3 语义：`T_world_lidar`，且与点云同坐标系

位姿是 **lidar → world**：`p_world = R · p_lidar + t`，`t` 是雷达光心在世界系的位置。第 2 节强调过，点云必须写在该位姿的传感器系下。

最常见的错配是**拿相机系位姿去变换雷达点云**（KITTI 的 `ground truth poses` 是 cam0 系）：

- 症状：单帧平面检测还正常（对称点云的协方差不受刚体变换影响），但世界系里每帧都被绕传感器轴额外转了一次 → 回环匹配全乱、TP 重叠率异常。
- 正确做法：`T_world_velo = T_world_cam0 · T_cam0_velo`，其中 `T_cam0_velo = R_rect · Tr_velo_to_cam`（见附录 A）。

另一类错配是"位姿是 IMU/body 系、点云是雷达外参后的系"，同样要乘上外参补齐。

### 4.4 行数、连续性与解析陷阱

- **行数必须等于帧数**。`pose.txt` 多了几行不会有问题（多出来的行没文件可读），少了则会少处理帧。注意日志里的 `Total submap number:N` 打的是 **pose 行数**（`pose_list.size()`，`src/example/place_recognition.cpp:391`），**不是实际处理的帧数**——所以它不能用来判断数据读全了没有。
- 解析是 `getline(sin, info, ' ')`，**严格按单空格切**。后果：

  | 写法 | 后果 |
  | --- | --- |
  | `0 1 2 3 0 0 0 1`（单个空格） | ✅ 正常 |
  | `0  1 2 3 ...`（连续两个空格） | ❌ 切出空 token，`>>` 解析为 0，**后面所有列整体错位**且不报错 |
  | `0\t1 2 3 ...`（用 Tab 分隔前两列） | ❌ Tab 不参与切分 → token 数 < 8 → 该行被丢弃，位姿数变少 |
  | 只有 7 列 | ❌ 该行被丢弃（`number == 7` 才 push），位姿数变少 |
  | 多于 8 列 | ⚠️ 只取前 8 列，多余列忽略 |
  | 行尾多一个空格 | ✅ 正常（`getline` 不会产生尾随空 token） |
  | 空行 | ⚠️ 被忽略，不产生位姿 |

  这些"静默错位"是位姿文件最危险的地方——务必用第 8 节的脚本卡一遍。

- 位姿序列本身可以是任意轨迹（不需要鲁棒平滑），但**真值位姿要真的对**：`cloud_overlap_thr` 的 TP/FP 判定用位姿算历史帧重叠率，位姿错了评估结果就没意义。

## 5. 配置文件 `config.yaml`

### 5.1 格式硬约束

- **首行必须是 `%YAML:1.0`**（OpenCV `cv::FileStorage` 的标记），否则打不开 → `Failed to open settings file at: ...` 然后 `exit(-1)`。
- 语法是 OpenCV FileStorage：`key: value`，`#` 注释，值不带引号。不是严格的 YAML（不能用列表/嵌套）。
- **键名写错 = 该参数为 0**，不报错（`fSettings["xxx"]` 返回空节点，隐式转 0）。两个著名的坑：
  - NMS 半径的键叫 `max_constrait_dis`（拼写就是 `constrait`，不是 `constraint`）；
  - 三角形边长放大系数叫 `triangle_resolution`，C++ 里叫 `std_side_resolution_`。
- 完整参数表见 [04-参数配置.md](04-参数配置.md)，这里只给一份可复制模板。

### 5.2 可复制模板（室内/小场景，即本示例使用的配置）

```yaml
%YAML:1.0

# 二值描述子（平面 + 投影图）
useful_corner_num: 500
plane_detection_thre: 0.01
plane_merge_normal_thre: 0.1
plane_merge_dis_thre: 0.3
voxel_size: 0.5
voxel_init_num: 10
proj_plane_num: 2
proj_image_resolution: 0.2
proj_image_high_inc: 0.1
proj_dis_min: -1.0
proj_dis_max: 4.0
summary_min_thre: 6
line_filter_enable: 0

# 三角形描述子
descriptor_near_num: 15
descriptor_min_len: 1
descriptor_max_len: 30
max_constrait_dis: 1
triangle_resolution: 0.2

# 候选检索 / 几何校验
skip_near_num: 100
candidate_num: 50
similarity_threshold: 0.7
rough_dis_threshold: 0.01
normal_threshold: 0.2
dis_threshold: 0.5
icp_threshold: 0.2
```

室外（KITTI）用 `src/config/config_outdoor.yaml`：`voxel_size: 2`、`proj_plane_num: 1`、`proj_image_resolution: 0.5`、`descriptor_min_len: 2`、`descriptor_max_len: 50`、`summary_min_thre: 10`，其余相同。

### 5.3 生成数据时要按你的数据调哪几个键

| 你的数据 | 要改的键 | 理由 |
| --- | --- | --- |
| 场景更小（<10 m 房间） | `voxel_size` 0.3–0.5、`proj_image_resolution` 0.1–0.2、`descriptor_min_len` 0.5–1 | 体素/网格要小于结构尺度，否则每格点数不足、关键点出不来 |
| 点数稀疏（<1e4/帧） | `voxel_init_num` 调小、`summary_min_thre` 调小、`proj_image_high_inc` 调大 | 关键点阈值是"格内占据箱数"，点少就意味着箱少 |
| 观测距离远（>50 m） | `descriptor_max_len` 调大、`proj_dis_max` 看情况 | 三角形边长上限决定了远近结构能否成为同一个描述子 |
| 回环帧间隔 < 100 | `skip_near_num` 必须小于该间隔 | 候选对要求 `frame_i - frame_j > skip_near_num_`（`src/src/btc.cpp:1626`），否则永远凑不出候选 |

## 6. 运行：ROS 参数

节点读的参数（`src/example/place_recognition.cpp:37-52`）：

| 参数 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `pcds_dir` | string | `""` | 帧文件所在目录（第 1 节） |

三种跑法：

```bash
# A. launch（改 src/launch/place_recognition.launch 里的默认值，或用参数覆盖）
roslaunch btc_desc place_recognition.launch
```

```bash
# B. rosparam set + rosrun（本仓库验证时用的方式；参数是全局的，前缀不带节点名）
roscore &
source /opt/ros/noetic/setup.bash
source <workspace>/devel/setup.bash
rosparam set /pcds_dir    /abs/path/my_dataset/velodyne
rosparam set /pose_file   /abs/path/my_dataset/pose.txt
rosparam set /setting_path $(rospack find btc_desc)/config/config_indoor.yaml

```

```bash
# C. 一次性的 params 文件
rosparam load my_params.yaml && rosrun btc_desc btc_place_recognition
```

输出（stdout）关键行：`Sucessfully load config file:...`（源码里就是拼错的 `Sucessfully`）、`Successfully load pose file:.... pose size:N`、每帧的 `[Description] submap id:k` 与 `[Description] reference plane normal:... center:...`、回环的 `[Loop Detection] triggle loop: i--j, score:...`，最后是 `Total submap number:..., triggle loop number:..., true loop number:...` 与平均耗时。

## 7. 数据质量要求（决定"能跑"还是"能出结果"）

格式对了只是第一步。描述子由**平面 + 平面上的投影占据图**构成（`extract_binary`，`src/src/btc.cpp:1076`），所以数据的**几何内容**直接决定能不能出关键点：

1. **必须有平面**。体素内点数 > `voxel_init_num` 且协方差最小特征值 < `plane_detection_thre`（0.01 m²）才判为平面。一帧一个平面都没有 → 该帧无描述子。室内墙面/地面/天花板很容易满足；纯草地、全曲面场景不满足。
2. **平面之外要有"离面结构"**。关键点来自"距离参考平面 `[proj_dis_min, proj_dis_max]`（默认 −1~4 m）内的点"，投影到网格后**同一格内沿法向占据多少个 0.1 m 高的箱**。所以：
   - 一面孤零零的平板 → 每格只有 1~2 层 → `summary < summary_min_thre` → 无关键点；
   - 墙 + 地面 + 箱子/柱子/车 → 格内有 3~10 层 → 出关键点。
   
   这就是室内配置 `proj_plane_num: 2` 的原因：一块墙面不够，用两面墙各产一组关键点。
3. **点数**：单帧 1e4~1e5 比较合适。本示例 2.2e4 点/帧，每帧两个参考面都稳定产出了关键点与三角形；点数掉到 1e3 量级时，网格里每格的占据箱数很难达到 `summary_min_thre`，关键点基本出不来。
4. **回环必须真的重复观测**：算法按三角形边长哈希检索，只有"同一片结构、同一尺度"的两次观测才能匹配上。设计轨迹时让传感器**走两圈以上**（回到起点、朝向相同），本示例 120 帧/圈、走 2 圈，回环间隔 120 帧，`skip_near_num=100` 才能凑出候选。
5. **尺度必须是米**。所有阈值都是米制的；把毫米当米写进去，得到的是"超大场景 + 巨大体素"。
6. **帧数上限**：`frame_number_` 是 `unsigned short`（`src/include/btc.h:84`），>65535 帧会回绕；`candidate_selector` 里 `double match_array[20000]`（`src/src/btc.cpp:1576`）在帧号 ≥20000 时越界。**请把单条序列控制在 20000 帧以内**（KITTI 00 只有 4541 帧）。
7. **位姿与点云一致性**（第 4.3 节）：不一致时单帧描述子看起来正常，但世界系点云错乱，回环和 TP 评估都会偏。

## 10. 故障速查

| 现象 | 原因 | 定位与修法 |
| --- | --- | --- |
| 只有 `Read End...`，随后 `Mean time ...: -nanms` | `%06d.bin` 打不开：`pcds_dir` 指错（指到数据集根而不是帧目录）、帧不是从 `000000` 开始、或 `read_bin=true` 但只有 `.pcd` | `ls $pcds_dir/000000.bin`；检查是否少了一层目录 |
| `[ERROR] Couldn't read file .../000005.pcd` 连续刷屏 | `read_bin=false` 但 PCD 缺文件 / `DATA binary_compressed` / `FIELDS` 缺 `x y z` / `POINTS` 与实际不符 | 用第 8 节脚本；`head -11 x.pcd` 看头；改用 `DATA ascii` 或 `binary` |
| `Total submap number:240` 但只看到很少的 `submap id:` | 帧文件比位姿行数少（bin 直接 break） | 对帧目录 `ls 目录 \| wc -l`，与 `wc -l pose.txt` 比 |
| 一句 `reference plane` 都没有 | 帧内没有平面：点数太少、`voxel_size` 远大于结构、场景全是曲面 | 看点数；换更小 `voxel_size`、更大 `plane_detection_thre` |
| `[ERROR] No STDescs!` | 该帧有平面但没出关键点/三角形：全是平板、`summary_min_thre` 太高、`proj_dis_*` 窗口没覆盖结构高度 | 让数据有离面结构；调 `summary_min_thre`（室内 6）；确认墙面在 ±4 m 内 |
| 能出平面、`No STDescs!` 也不报，但 `triggle loop number:0` | `skip_near_num`(100) ≥ 回环帧间隔；轨迹没重复；`descriptor_min_len/max_len` 与场景尺度不匹配；`similarity_threshold` 0.7 太高 | 回环间隔 120 时 `skip_near_num` 设 100 可行；测 30 帧短序列时必然 0 回环，属正常 |
| 回环很多但 `true loop` 很少（大量 FP） | 位姿与点云坐标系不一致（cam0 vs velodyne）、场景强重复（对称走廊） | 核对位姿外参；看 TP/FP 可视化里的相对位姿 |
| `pose size:` 比 `wc -l pose.txt` 小 | 位姿行被丢弃：Tab 分隔、列数 ≠ 8、连续空格 | 用第 8 节脚本逐行报行号 |
| 位姿全对但世界系点云"绕轴乱转" | 用相机系位姿变换雷达点云 | 按 4.3 节乘 `T_cam0_velo` |
| 参考平面中心整体偏移一个常数 | 点云与位姿的原点不一致（如位姿给的是 IMU，点云是雷达外参后的） | 统一到同一外参 |
| 段错误 / `match_array` 越界 | 序列 ≥20000 帧，或 >65535 帧导致 `unsigned short` 回绕 | 拆分序列 |
| `Failed to open settings file at: ...` 后直接退出 | YAML 首行缺 `%YAML:1.0`，或路径含中文/不存在 | 补首行；用绝对路径 |

## 附录 A：从 KITTI 或别的数据集转换

**KITTI velodyne + 官方 GT 位姿**：`data_odometry_poses/dataset/poses/00.txt` 每行是 12 个数（3×4 矩阵，行主序，cam0 系）。转成本项目的 8 列需要两步：

1. 补成 4×4：`T_world_cam0 = [[R|t],[0 0 0 1]]`；
2. 换到 velodyne 系：`T_world_velo = T_world_cam0 @ T_cam0_velo`，`T_cam0_velo = R_rect @ Tr_velo_to_cam`（`R_rect` 来自 `calib.txt` 的 `R_rect`，`Tr_velo_to_cam` 是 3×4 的 velo→cam0）。

```python
import numpy as np
from scipy.spatial.transform import Rotation as Rot

def kitti_gt_to_8col(gt_file, calib_file, out_file):
    # calib.txt: R_rect: r11 .. r33 ; Tr: t11 .. t34 (3x4)
    vals = {}
    for line in open(calib_file):
        key, _, rest = line.partition(":")
        vals[key.strip()] = np.array([float(x) for x in rest.split()])
    T_velo_cam = np.eye(4)
    T_velo_cam[:3, :] = vals["Tr"].reshape(3, 4)
    R_rect = np.eye(4)
    R_rect[:3, :3] = vals["R_rect"].reshape(3, 3)
    T_cam0_velo = R_rect @ T_velo_cam          # velo -> cam0
    lines = []
    for i, line in enumerate(open(gt_file)):
        T_w_cam0 = np.eye(4)
        T_w_cam0[:3, :] = np.array([float(x) for x in line.split()]).reshape(3, 4)
        T_w_velo = T_w_cam0 @ T_cam0_velo
        t = T_w_velo[:3, 3]
        qx, qy, qz, qw = Rot.from_matrix(T_w_velo[:3, :3]).as_quat()  # xyzw
        lines.append("%d %.6f %.6f %.6f %.6f %.6f %.6f %.6f"
                     % (i, t[0], t[1], t[2], qx, qy, qz, qw))
    open(out_file, "w").write("\n".join(lines) + "\n")
```

（`Rot.as_quat()` 返回 `x y z w`，正好是本文件的列序；仓库自带的 `src/poses/kitti00.txt` 已是转换好的结果，可直接用于 KITTI 00 的 velodyne。）

**其他来源**：

- **TUM / evo 的 `x y z qx qy qz qw`**：列序一致，加一列序号即可直接用。
- **只有世界系地图、没有逐帧位姿**：把每帧点云写世界系，位姿全写 `0 0 0 0 0 0 0 1`（id + 零平移 + 单位四元数）。
- **只有 SLAM 里程计 + 累积点云**：需要回到"单帧雷达系"或至少"每帧局部系"，不能直接把累积地图当单帧（会把历史结构的点算成当前观测，`summary` 与三角形全都错）。

## 附录 B：生成数据的最小骨架

```text
for k in 0..N-1:
    P_sensor = 该帧在传感器系下的点 (N_k, 3)      # 米
    write  P_sensor 拼上第四列 → velodyne/%06d.bin
    write  "%d x y z qx qy qz qw\n" % (k, 位姿)    # 同一坐标系、单位四元数
```

约束回顾（全部在第 2–7 节展开）：`%06d` 连续编号；每点 4×float32；点云=传感器系、位姿=lidar→world；8 列单空格、w 在最后且 `||q||=1`；帧数=位姿行数；单位米；场景里要有平面 + 离面结构；回环要真的重访；`skip_near_num` < 回访帧间隔；序列 < 20000 帧。
